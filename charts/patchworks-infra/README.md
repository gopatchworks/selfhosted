# Patchworks Infrastructure Chart — Configuration Reference

The `patchworks-infra` chart owns baseline infrastructure resources for a
Patchworks install: MySQL, Redis, RabbitMQ, Elasticsearch, S3/MinIO, KubeFaaS,
Soketi, and optional infrastructure dependencies.

Use it with the `patchworks-app` chart and pass the same values file to both:

```bash
helm upgrade --install patchworks-infra ./charts/patchworks-infra -f values.yaml
helm upgrade --install patchworks-app ./charts/patchworks-app -f values.yaml
```

Resource names default to the stable `patchworks` prefix, not the Helm release
name, so the infra and app charts can be installed as separate releases while
sharing service and Secret names.

When `credentials.autoGenerate=true` (default), empty in-cluster infra
credentials are generated by a `pre-install,pre-upgrade` hook Job before the
infra workloads start. Existing Secrets are left untouched on upgrades.

The app chart owns migration and seeding hooks, but this chart keeps the same
values API so a shared values file can be passed to both releases.

## Installation profile

`profile` is shared with the app chart through one values file (see the app
chart's [Installation profile](../patchworks-app/README.md#installation-profile)).
Under `profile: lightweight`, the bundled Elasticsearch, RabbitMQ, Soketi and
KubeFaaS request less memory, so the release and an ingress controller can be
scheduled on a small single node. On a 4 GB Raspberry Pi 5, the kubelet's system
reservation left 3021Mi allocatable. There, Contour's 192Mi of requests and the
infra chart's standard 1792Mi left too little for the gateway. With both charts
on the lightweight profile, the release requests about 1.9 GiB.

KubeFaaS's standard requests, about 1.6 GiB, didn't fit next to that release:
the builder stayed Pending. Under the profile it runs one controller and
requests 240Mi with the bundled registry. Each script Core deploys adds a pod
requesting 35M, Core's own request, which runs until 24 hours after the script's
last call. With k3s's and Contour's pods and one deployed script, about 500Mi of
the Pi's 3021Mi stays free. The app chart's gateway, processor and Monocore
roll without a surge under the profile, so their upgrades don't need it. It
leaves room for the pods that still surge here, the largest being the builder
(176Mi). These figures cover scheduling only. The builder's image builds were
not measured on the Pi. They run in dind against its 2Gi limit, not its 128Mi
request, and under swap limits that follow requests (as with k3s's
`LimitedSwap`), the smaller request also means less swap for them.

| Key | Default | Description |
|-----|---------|-------------|
| `profile` | `standard` | `standard` or `lightweight` |
| `lightweight.elasticsearch.javaOpts` | `-Xms256m -Xmx256m` | Replaces `elasticsearch.javaOpts`: a heap at half the request below. Search over a large history needs the standard heap |
| `lightweight.elasticsearch.resources` | requests memory `512Mi` | Goes over `elasticsearch.resources` (`1Gi`). Elasticsearch used about 990Mi with the 512m heap |
| `lightweight.rabbitmq.resources` | requests memory `256Mi` | Goes over `rabbitmq.resources` (`512Mi`); the `1Gi` limit stays. RabbitMQ used about 80–130Mi |
| `lightweight.soketi.resources` | requests memory `128Mi` | Goes over `soketi.resources`, whose limits otherwise also count as the request (`256Mi`). Soketi used about 45Mi |
| `lightweight.kubefaas.controller.replicaCount` | `1` | Replaces `kubefaas.controller.replicaCount` (`3`). `null` keeps it |
| `lightweight.kubefaas.controller.resources` | requests memory `32Mi` | Goes over `kubefaas.controller.resources` (`128Mi`). The controller used about 13–22Mi |
| `lightweight.kubefaas.redis.resources` | requests memory `16Mi` | Goes over `kubefaas.redis.resources` (`512Mi`); the `768Mi` limit stays. Redis used about 7Mi |
| `lightweight.kubefaas.registry.bundled.resources` | requests memory `16Mi` | Goes over `kubefaas.registry.bundled.resources` (`64Mi`). The registry used about 5Mi |
| `lightweight.kubefaas.builder.resources` | requests memory `32Mi` | Goes over `kubefaas.builder.resources` (`128Mi`). Its `registry-proxy` sidecar keeps `16Mi` |
| `lightweight.kubefaas.builder.dind.resources` | requests memory `128Mi` | Goes over `kubefaas.builder.dind.resources` (`512Mi`); the `2Gi` limit stays for image builds |
| `lightweight.kubefaas.functions.profile.resources` | requests memory `16M` | Replaces `kubefaas.functions.profile.resources` (`128M`), the request of a function pod that doesn't set its own. A string, so it replaces the profile's rather than merging. Core's scripts set their own (`35M`), which wins |

Each `resources` block goes over the component's own: its requests replace the
component's, and the component's other settings, such as `cpu` and `limits`,
stay. Each `lightweight.kubefaas` block goes over the `kubefaas` block at the
same path. Set a block to `null` to use the component's settings alone. Requests
only reserve memory: a node that schedules every pod can still run short when
they get busy, and KubeFaaS's image builds do. MySQL, Redis and S3 are
unchanged.

## Pod DNS

Set top-level `ndots` in the shared values file to configure pod DNS in both
charts. Every chart-managed Deployment, Job and CronJob inherits it. The most
specific non-null, non-empty setting wins; numeric `0` is supported. With no
setting at any level, the chart omits `dnsConfig` entirely and leaves Kubernetes
DNS behaviour unchanged. No numeric default is supplied.

All keys below are optional and unset by default. Each path supports `.ndots`;
chains run from less to more specific, after the top-level setting.

| Workload | Override chain |
|----------|----------------|
| Gateway / Start | `web` → `web.gateway` / `web.start` |
| Fabric, Dashboard, S3 Manager | `fabric`, `dashboard`, `s3Manager` respectively |
| Standalone workers | `workers` → `workers.hub` or `workers.companies[]` |
| Microservice workers | `workers` → `workers.microservices._default` → `workers.microservices.<service>` → `workers.hub` or `workers.companies[]` → `workers.companies[].microservices.<service>` |
| Mono workers | `workers` → `workers.mono` → `workers.hub` or `workers.companies[]` |
| Processor Deployments | `workers` → `processorDeployments` → `processors[]` |
| Scheduler CronJobs | `workers` → `scheduler` → `processors[]` → `processors[].scheduler` |
| Core / Fabric migrations | `migrations`; Fabric also inherits `fabric` before `migrations`, then `fabric.migrations` |
| Seed Jobs | `seeds` → `seeds.fabric`, `seeds.tenant` or `seeds.core`; Fabric seed Jobs also inherit `fabric` before `seeds` |
| MySQL, Redis, RabbitMQ, Elasticsearch, MinIO | `mysql`, `redis`, `rabbitmq`, `elasticsearch`, `s3` respectively; setup Jobs and the RabbitMQ Recreate hook inherit their component |
| Fabric MySQL / Redis | `fabric` → `fabric.mysql` / `fabric.redis` |
| KubeFaaS controller / builder / Redis | `kubefaas` → `kubefaas.controller` / `kubefaas.builder` / `kubefaas.redis` |
| Native Soketi | `pusher` → `soketi` |
| RabbitMQ topology Job | `rabbitmq` → `rabbitmq.topology` |
| Credential generators | `credentials` → `credentials.generator`; app key, Passport and Pusher generators then apply `app`, `passport` or `pusher`; tenant password generation then applies `seeds` → `seeds.tenant` |
| Mono store generator | `workers` → `workers.mono` → `credentials` → `credentials.generator` |

For example:

```yaml
ndots: 2
web:
  ndots: 1
  gateway:
    ndots: 0
workers:
  ndots: 1
  microservices:
    batch:
      ndots: 3
```

This sets Gateway to `0`, Start and workers to `1`, the batch microservice to
`3` when microservice mode is enabled, and other chart-managed pods to `2`.

The optional upstream Soketi subchart and function pods created dynamically by
the KubeFaaS controller are managed outside these pod templates and do not
inherit this setting.

## Passport OAuth keys

Both Core and Fabric use [Laravel Passport](https://laravel.com/docs/passport) for OAuth token signing and verification. They share a single RSA key pair:

- **`PASSPORT_PRIVATE_KEY`** — used by Fabric to sign JWT tokens.
- **`PASSPORT_PUBLIC_KEY`** — used by both Core and Fabric to verify them.

### Auto-generation (default)

On `helm install`, a `pre-install` hook Job runs `openssl genrsa` inside an `alpine` container, creates the key pair, and stores it in a Kubernetes Secret called `<release-name>-passport-keys`. The Secret is annotated with `helm.sh/resource-policy: keep` so it is **never deleted** by Helm — not on `helm upgrade`, not on `helm uninstall`. The Job is idempotent: on subsequent upgrades it checks whether the Secret already exists and exits immediately if so.

No configuration is required for the default behaviour.

### Bringing your own keys

If you want to supply pre-generated keys (recommended for production), generate an RSA key pair and create the Secret before installing the chart:

```bash
# Generate a 4096-bit RSA private key and derive the public key
openssl genrsa -out passport.key 4096
openssl rsa -in passport.key -pubout -out passport.pub

# Create the Secret in the release namespace
kubectl create secret generic my-passport-keys \
  --from-file=PASSPORT_PRIVATE_KEY=passport.key \
  --from-file=PASSPORT_PUBLIC_KEY=passport.pub

# Remove the local key files
rm passport.key passport.pub
```

Then reference it in your values:

```yaml
passport:
  existingSecret:
    name: my-passport-keys
    privateKeyKey: PASSPORT_PRIVATE_KEY   # default, change if your keys differ
    publicKeyKey: PASSPORT_PUBLIC_KEY     # default, change if your keys differ
```

When `passport.existingSecret.name` is set the auto-generation Job, ServiceAccount, and RBAC are not created.

### Multi-namespace deployments

The generated Secret lives in the Helm release namespace (where Core runs). Fabric pods load it from that namespace. If you override `fabric.namespace` to place Fabric in a different namespace, copy the Secret there manually or use `passport.existingSecret` to point at a copy you manage.

| Key | Default | Description |
|-----|---------|-------------|
| `passport.existingSecret.name` | `""` | Existing Secret name. Leave empty to auto-generate |
| `passport.existingSecret.privateKeyKey` | `PASSPORT_PRIVATE_KEY` | Key within the Secret for the private key |
| `passport.existingSecret.publicKeyKey` | `PASSPORT_PUBLIC_KEY` | Key within the Secret for the public key |

## Processor Shared Values

The infra chart does not render processor workers, but it keeps
`processors[]` in the shared values file so the app chart can consume the same
configuration. The default app chart processor list creates worker Deployments
for `start`, `gateway`, `short-processor`, `medium-processor`,
`long-processor`, and `logging`. The `logging` processor disables its scheduler
by default because it only consumes application broadcast/logging work.

### Path-based routing and prefix stripping

When `ingress.provider=contour`, each configured public host is rendered as a
Contour `HTTPProxy`. The dashboard host uses one `HTTPProxy` containing:

- `/` routed to the dashboard service.
- `/fabric`, `/core-main`, and `/core-start` routed to their respective services
  with the prefix stripped before forwarding.

When `ingress.provider=nginx` or `other`, the dashboard host creates two
standard Ingress resources:

- **`patchworks-dashboard`** — routes `/` to the dashboard service.
- **`patchworks-dashboard-routes`** — routes `/fabric`, `/core-main`, and
  `/core-start` to their respective services.

When `dashboard.routingMode=path`, empty dashboard service URLs use these
same-origin routes by default. When `dashboard.routingMode=host`, empty
dashboard service URLs use the dedicated `ingress.hosts.*` hostnames when
configured.

`ingress.hosts.webhook` and `ingress.hosts.callback` create dedicated public
routes to the Core start service. This matches the production Haberdashery
layout where `webhooks.*` and `callbacks.*` are separate public hosts handled by
Core Start. The same host values are also injected into Core application pods as
`WEBHOOK_DOMAIN` and `CALLBACK_DOMAIN`.

> ⚠️ **`ingress.rewriteAnnotations` is only used with standard Ingress providers.** Contour uses `HTTPProxy.pathRewritePolicy` directly. If you use nginx or another Ingress controller, configure rewrite annotations for that controller.

#### Contour (default)

No rewrite annotations are needed. The chart renders `HTTPProxy` resources and
uses `pathRewritePolicy` for the dashboard `/fabric`, `/core-main`, and
`/core-start` routes.

#### nginx-ingress

nginx requires a regex capture group in the path and a different annotation. Set `rewriteAnnotations` and override the path patterns via `annotations`:

```yaml
ingress:
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
  rewriteAnnotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
```

> **Note:** nginx also requires the path patterns to include a capture group (e.g. `/fabric(/|$)(.*)`). Because Kubernetes Ingress path patterns are not configurable per-path in Helm without a full template override, nginx users may prefer to set `ingress.enabled=false` and manage Ingress resources manually or via a separate chart.

#### Traefik

Use a `StripPrefix` middleware and reference it via an annotation:

```yaml
# First create the middleware in the same namespace:
# kubectl create -f - <<EOF
# apiVersion: traefik.io/v1alpha1
# kind: Middleware
# metadata:
#   name: patchworks-strip-prefix
# spec:
#   stripPrefix:
#     prefixes: ["/fabric", "/core-main", "/core-start"]
# EOF

ingress:
  rewriteAnnotations:
    traefik.ingress.kubernetes.io/router.middlewares: "<namespace>-patchworks-strip-prefix@kubernetescrd"
```

RabbitMQ names its node `rabbit@<hostname>` and keeps the node's queues,
messages and definitions in `/var/lib/rabbitmq/mnesia/rabbit@<hostname>` on the
PVC. The chart pins the pod hostname so that every new pod finds that
directory. The chart doesn't set `RABBITMQ_NODENAME`: the broker and its
probes must resolve the node's host part, and a pod resolves only its own
hostname.

Only one broker may use that directory at a time:

- **Rollouts.** The Deployment uses the `Recreate` strategy, so the old broker
  stops before the new pod starts.
- **Deleted or evicted pods.** The ReplicaSet starts the replacement while the
  old pod is still stopping, and on the same node both mount the volume. The
  container therefore runs the image's `docker-entrypoint.sh rabbitmq-server`
  under a `flock` on `/var/lib/rabbitmq/.broker.lock`, and the new broker
  waits for the old container to exit. On storage without `flock` it logs this
  and starts at once.
- **Custom images.** An image set in `rabbitmq.image` needs `sh`, `flock` and
  that entrypoint, as the official `rabbitmq` images have.

### Upgrading to a fixed node name

Earlier charts used the pod name as the hostname. Every rollout, eviction or
reschedule therefore started an empty broker under a new node name. The first
upgrade to this chart changes the node name once more:

- **Strategy.** Before the upgrade applies, the `pre-upgrade` hook Job
  `<fullname>-rabbitmq-recreate` patches the live Deployment to `Recreate`. It
  uses `credentials.generator.image`, which can be any image with `kubectl`.
  - **Why it's needed:** under server-side apply, which Helm 4 and the
    installer use, the upgrade would otherwise fail with
    `spec.strategy.rollingUpdate: Forbidden`.
  - **No restart:** the patch doesn't restart RabbitMQ.
  - **When it renders:** once the Deployment uses `Recreate`, the hook no
    longer renders. The exception is `helm template` and Argo CD, which have no
    `lookup`: there the hook always renders, runs and changes nothing.
  - **Patching by hand instead:** run this before upgrading and Helm skips
    the hook:

    ```bash
    kubectl -n <namespace> patch deployment <fullname>-rabbitmq --type=merge -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'
    ```
- **Data, by default.** The new pod starts an empty broker as
  `rabbit@<fullname>-rabbitmq`. Upgrade the app release afterwards; the
  installer does both.
  - **What comes back:** the app release's `rabbitmq-topology` hook recreates
    the processor queues and the hub worker queues. Monocore workers assert
    their own topology when they start.
  - **What doesn't come back:**
    - messages queued at the time of the upgrade;
    - company queues and bindings created by hand for standalone and
      microservice workers;
    - users, policies and vhosts added by hand.
- **Data, kept.** To keep the broker as it is, set `rabbitmq.hostname` to the
  current RabbitMQ pod's name before upgrading. Keep it set on every later
  upgrade: removing it moves the node to `rabbit@<fullname>-rabbitmq`, which
  starts empty. To find the pod's name:

  ```bash
  kubectl -n <namespace> get pods -l app.kubernetes.io/name=rabbitmq,app.kubernetes.io/instance=patchworks-infra -o name
  ```

- **Old directories.** Each earlier pod left a `rabbit@<pod name>` directory
  under `/var/lib/rabbitmq/mnesia`, with `-feature_flags` and `-plugins-expand`
  siblings. Nothing reads them, so you can delete them to free space on the
  volume. To list them:

  ```bash
  kubectl -n <namespace> exec deploy/<fullname>-rabbitmq -- ls /var/lib/rabbitmq/mnesia
  ```

## KubeFaaS

Optional serverless function execution layer. Disabled by default. Under
`profile: lightweight` it runs one controller and requests less memory (see
[Installation profile](#installation-profile)).

When `kubefaas.enabled`, `kubefaas.auth.enabled`, and `credentials.autoGenerate` are all true, missing auth credentials are generated into `<release>-kubefaas-auth` in both the KubeFaaS namespace and the app release namespace. The app chart consumes the release namespace copy. For external KubeFaaS, provide both inline auth values or `kubefaas.auth.existingSecret.name`.

The chart renders both copies itself from one login, not the credential generator Job, because the KubeFaaS namespace doesn't exist yet when that Job runs. A generated login is kept across upgrades by looking up the existing Secret; a copy that this release didn't create, such as one an earlier chart's generator wrote, is left alone and its login reused. `helm template` and Argo CD can't look Secrets up, so there a generated login changes on every render: set `kubefaas.auth.username` and `kubefaas.auth.password`, or `kubefaas.auth.existingSecret.name`, to pin it.

### CRDs and function profiles

The KubeFaaS controller keeps functions and profiles as cluster-scoped custom
resources, `Function` and `Profile` in `kubefaas.patchworks.io/v1alpha1`. Their
CRDs are in `crds/`, copied from the KubeFaaS release the images are built from.
Without them the controller logs `the server could not find the requested
resource` and no script can be deployed.

Helm applies `crds/` only when it first installs a release, whatever
`kubefaas.enabled` says, and never changes a CRD that exists. The installer
applies them itself before every infra install or upgrade with KubeFaaS on. With
the Helm CLI, apply them before upgrading a release that turns KubeFaaS on, or
after a chart update:

```bash
kubectl apply --server-side --field-manager=helm --force-conflicts -f charts/patchworks-infra/crds/
```

Otherwise the upgrade fails with `no matches for kind "Profile"`. Uninstalling
the release leaves the CRDs and the `Function` resources in place.

Core names a profile when it deploys a script, and the controller refuses a
function whose profile doesn't exist ("profile not found"), except `default`.
`kubefaas.functions.profiles` renders one `Profile` per key, named after it, with
the value as its `spec` (the fields in `crds/kubefaas.io_profiles.yaml`):

| Profile | What it sets |
|---|---|
| `default` | `enableServiceLinks: false` |
| `test` | Pods stop, and the function is deleted, 30 minutes after its last call (`shutdownAfterInactive`, `autoDeleteAfter`) |
| `autoscaling` | For functions that fail their health checks under load: `125m` and `256M` per pod, 2 to 10 pods at 80% CPU, `maxUnavailable: 1` disruption budget, a liveness probe that allows 7 failures 10 seconds apart; pods stop after 2 hours idle and the function is deleted 36 hours after its last call |

A profile without `resources` gets `kubefaas.functions.profile.resources`, or
`lightweight.kubefaas.functions.profile.resources` (`16M`) under
`profile: lightweight`. `autoscaling` keeps its own, so a function on it
requests at least 512M on a small node. Override a field with the same key
(`kubefaas.functions.profiles.autoscaling.autoscaler.maxReplicas: 4`), add a
profile with a new key, or set a key to `null` to leave it out.

These replace the `profile-default` ConfigMap earlier charts rendered, which the
controller no longer reads.

### The builder's S3 login

The builder runs in the KubeFaaS namespace and caches images in S3, but the S3
login's Secret is in another namespace (`patchworks-s3-auth`, or your
`existingSecret`), and a Pod can only read Secrets in its own. The chart
therefore copies the login into `<release>-kubefaas-s3` in the KubeFaaS
namespace:

- **Inline login** (`s3.auth.rootUser`/`rootPassword`, or
  `s3.external.accessKey`/`secretKey`): the builder gets the values directly,
  with no copy.
- **A Secret that exists**, the generated one or yours: the chart reads it with
  `lookup` and copies it.
- **A login the credential generator has yet to create** (a first install):
  the chart generates it while rendering, and hands it to the generator Job,
  which writes it to `patchworks-s3-auth`. The copy and the Secret therefore
  agree.

`helm template` and Argo CD can't look Secrets up. There, a generated login
changes on every render while the generator keeps the first, so set the S3
login inline. With your own `existingSecret`, the builder names it as before,
so create it in the KubeFaaS namespace too.

### Bundled image registry

The builder pushes every image it builds, the base image of each function
template and each function, to a registry, and function pods pull them from it.
With `kubefaas.registry.bundled.enabled` the chart runs that registry in the
KubeFaaS namespace (`kubefaas-registry.yaml`) for installations without one of
their own:

- The registry (`registry:2`) keeps images on a PersistentVolumeClaim and
  requires a login, written to its htpasswd file by an init container.
- Images are named `localhost:<nodePort>/...`. Each node's container runtime
  pulls them through the registry's NodePort on its own localhost, which
  containerd reaches over plain HTTP without configuration.
- The builder pushes to the same name through a `registry-proxy` sidecar that
  forwards `127.0.0.1:<nodePort>` to the registry Service. Docker treats
  localhost as an insecure registry, so the dind daemon needs no configuration
  either.
- The chart renders the login, `registries.yaml` for the builder (the
  `kubefaas.registry.name` and `kubefaas.builder.baseImagesRegistry` entries)
  and a `kubernetes.io/dockerconfigjson` pull Secret in the KubeFaaS namespace
  and every function namespace, which the function ServiceAccounts list. A
  generated login is kept across upgrades the same way as the KubeFaaS auth
  login.

On k3s, which runs containerd with kube-proxy in iptables mode, a push from a
dind daemon through the proxy and a pull by containerd with the pull Secret have
been checked. Nodes that use another runtime, or whose kube-proxy doesn't route
NodePorts on localhost (IPVS mode, or a kube-proxy replacement), need a registry
of their own in `kubefaas.registry.config`. The bundled registry renders its own
`registries.yaml`, so the chart fails when `kubefaas.registry.config` or
`kubefaas.registry.existingSecret.name` is also set.

```yaml
kubefaas:
  enabled: true
  builder:
    platform: linux/arm64   # arm64 nodes
  registry:
    bundled:
      enabled: true
```

The builder reports ready (`/v1/readyz`) only once it has built the base image
of every function template, one at a time, so the first install with KubeFaaS
can take a long time: allow `--timeout 60m` or more. Until then the builder
Service has no endpoints, so a script deployed meanwhile fails to reach the
builder instead of building on a base image that isn't there yet. On a
Raspberry Pi 5 each base image took from about 40 seconds to 5 minutes. The KubeFaaS controller and builder
images come from the same registry as the application images, so the image
pull Secret named in `image.pullSecrets` must also exist in the KubeFaaS
namespace; the installer copies it there.

When upgrading a cluster where the cert-manager CA has already rotated, force-renew the
`<release>-kubefaas-docker-server` and `<release>-kubefaas-docker-client` Certificates once
after applying this chart, then restart the builder Deployment. Cert-manager does not
automatically replace an unexpired leaf certificate solely because its issuing CA changed.
